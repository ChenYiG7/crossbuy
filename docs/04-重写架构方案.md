## 0. 一句话方案

> **R1 = 在不动数据库的前提下，用全 TS 栈把旧系统三个项目的功能 1:1 复现**：Next.js 三前台（web/mzk/admin）+ Fastify 机器面 API（open API / webhook）+ BullMQ worker（替代 56~58 个 Job），经防腐层直接读写现有 PolarDB 旧表；按域绞杀 PHP、灰度切流、随时可回退。数据库重构（R2）、账本/四方对账、认证中心、系统拆分（R3）全部后置——但**模块边界现在就按 R3 拆分形态设计**（见第 3、12 章）。

| 层 | 选型 | 与 docs/01 的关系 | 说明 |
|----|------|------------------|------|
| 前台（web/mzk） | Next.js 15 App Router + Tailwind + shadcn/ui | 不变 | 客户面重做，URL/页面结构 1:1 平移保 SEO |
| 后台（admin） | Next.js 15（同栈） | 不变 | 替代 dcat-admin，RuoYi Vue3 的角色等价物 |

| 队列/定时 | apps/worker（BullMQ + Redis） | 不变 | 替代旧 56~58 个 Job（两文档口径不一，以绞杀时 JIT 盘点为准） |

1. **GraphQL 保真这个最大风险项直接消失**：Java 1 期必须复刻 177 ops 逐字段等价（前端零改动的前提）；本方案前台全部重做，客户面直接上 REST，无兼容包袱。
2. **零数据迁移、零双写**：新系统直接读写旧表，切换 = 写入口 + 流量切换，不存在新旧表同步。旧策略（同库双写新旧表 + T0~T3 时序）整体后移到 R2。

## 2. 目标架构与部署拓扑

        │              │                │                  │
        │  /api/customer/v1/**（各自 BFF 路由 + RSC 直调域服务）  │  /api/admin/v1/**
        └──────────────┴────────┬───────┴──────────────────┘

**关键决策 D1：接口面归属**

| 接口面 | 路径 | 承载 app | 认证 |
|--------|------|----------|------|
| 客户面 | `/api/customer/v1/*` + RSC 直调 | apps/web、apps/mzk（各自挂载） | Auth.js JWT（dfFlag 分流代发用户） |
| 后台面 | `/api/admin/v1/*` | apps/admin | Session + Redis |
| 开放面 | `/api/open/v1/*` | apps/api | API key/签名（平移旧开放 API 语义） |
| 回调面 | `/api/webhook/v1/{provider}` | apps/api | 强制签名校验 + IP 白名单 |

- **人类面 API 留在各自 Next app**（BFF + RSC 直调域服务，同进程零网络跳）——这是 monorepo 的核心红利，也守住 docs/01「Next.js 全栈能力」定版；
- **机器面独立成 apps/api（Fastify）**，理由：① 安全基线不同（签名/IP 白名单/限流）；② 独立伸缩与发布；③ R3 拆分时天然是独立服务候选；④ 与 worker 同为纯 Node 服务，无新范式。

**关键决策 D2：域逻辑全部下沉 `packages/domains/*`，apps 只做薄壳**。app 的 route/页面只做「contract zod 校验 → 调域服务 → 渲染」，业务逻辑零散落在 app 里。R3 拆分时把域包整体搬出即为服务，apps 与 contract 都不用改语义。

**关键决策 D3：部署粒度与发布策略（仓库 ≠ 部署单元，2026-10-17 拍板）**

> 五个 app（web/mzk/admin/api/worker）= **五个独立部署单元**：各自独立构建产物（Next.js standalone / 纯 Node 进程）、独立发布节奏、独立进程。改一个后台页面 → 只构建并发布 admin（turbo 依赖图保证其余缓存命中），web/mzk 线上进程零感知。

- **无共享后端进程**（D1 的直接推论）：客户面 API 在 web/mzk 进程内、后台面在 admin 进程内、机器面在 apps/api——**admin 后端发版不影响客户后端**，客户前端不受牵连。
- `packages/domains/*` 与 `packages/contract` 是**构建期编译副本**打进各进程产物，运行时零跨进程 import；admin 发新版不会替换 web 进程内正在运行的域代码。运行时唯一共享状态 = MySQL + Redis（与发版无关）。
- **发布影响半径（blast radius）按改动类型分级**：

| 改动类型 | 需发布的进程 |
|---|---|
| 单个 app 的页面 / 自身路由 | 只有该 app |
| packages 只读逻辑（查询 / UI） | 依赖它的 app，各自择机发 |
| 域写路径行为 / 契约破坏性变更 | 该域全部写方进程同窗口协同发（M0.8 起 CI 按 diff 自动列出清单，清单外明确标注「无需发版」） |

- **版本偏斜纪律**：域写路径变更后未协同发布的写方进程仍跑旧代码写同一张表——这是多写方系统的固有约束（旧系统 PHP 并存期同理），靠上面的分级发布纪律管住，不靠「全量重发」；契约向后兼容（只加字段不改语义）时协同发布可省。
- **回滚 = nginx upstream 切回旧产物目录**（蓝绿双 upstream，秒级，不重新构建）。
- 单仓红利：所有 app 构建时吃同一份 `packages/ui` / `contract`，从根上消灭「web 用 ui v1、admin 用 ui v2」的多仓版本漂移。

### 3.2 拆分就绪纪律（现在执行，R3 才兑现）

1. **表唯一属主**：174 张旧表逐张登记属主域（M0 产出映射表，底稿 = docs/plans/00）；跨域读**只走属主域的 service 接口**，禁直连别域表——即使旧库的多态外键（`oid`/`tid` 之类）天然诱导跨域 JOIN，也必须在属主域的 repository 内收口。
2. **域间禁横向 import**：跨域调用走 service 接口；跨域**反应**走**契约事件**（`contract/events` 定义事件 schema，进程内 pub/sub 实现，R3 可无痛换 MQ/Outbox）。
3. **contract 无框架/ORM 类型**：域服务出入参 = contract 类型；这是 R3 从「进程内调用」切「网络调用」时唯一的改造面。
4. **auth 抽象 principal**：域服务只认 `Principal`（谁、什么端、什么公司），不出现 Auth.js/Session 细节（见 §6）。
5. apps 全部独立部署（域名/发布节奏本来就不同），域包零 Next 依赖（可在 worker / apps/api 复用是验收标准）。
6. **纪律靠工具不靠自觉**：上述 1/2/3 条全部下到 ESLint 边界规则进 CI——`PrismaClient` 仅允许出现在 `domains/*/repository`、域间 import 禁止、`contract` 禁 ORM/框架类型；M0 落地时**故意写一个违规样例验证 CI 会拦**（守卫有效性是破坏出来的，不是看出来的）。

### 3.3 新域准入判据（2026-10-17 拍板）

> 业务线（普通代购 / mzk 代发 / 未来 FBA）是**端 × 域的编排**，不是模块。按业务线建模块会让订单/支付/物流能力在各业务线里重复一份，表属主制度被直接破坏（一张 `dg_order` 不能同时属于「代购模块」和「FBA 模块」）。**禁预建空域**——无人认领的空域是边界纪律的漏洞（「不知道代码放哪就丢进去」），ESLint 拦得住 import 越界、拦不住职责误放。

新增域包必须满足以下判据**之一**，否则用现有域编排：

| 判据 | 含义 |
|---|---|
| 独占表族 | 有自己独有的表（表属主能登记，M0.5 映射不冲突） |
| 独立所有权 | R3 时会有独立团队/系统认领（如财务系统） |
| 独立伸缩/部署 | 负载特征要求单独部署（如 webhook 高频回调） |

- **FBA 裁定**：FBA 头程 = send-order/logistics（履约）+ platform（Amazon 对接已在该域清单）+ finance（收费）的编排，挂在 mzk 端流程分支——**不建模块**；若未来出现独占表族（FBA 入库单 / 箱规 / 预约表），按上表判据新建 `fulfillment` 域（`scripts/scaffold-domains.mjs` 分钟级生成 + ESLint 边界自动覆盖 + 表属主登记一行）。待业务确认，见 TODO #15。
- 端与域是**正交两轴**：web/mzk/admin/api/worker 是端（谁在用），oms/财务/CRM 是域分组（R3 按域拆系统，端全部保留为各系统的客户端）——「web/mzk 属于 OMS」的说法不成立，web 横跨 CRM/OMS/财务所有能力。

## 4. 接口策略（全部 REST，契约先行）

1. **无 GraphQL**。客户面直接定义新 REST 契约——已完成的 `contract/domains/{member,order,send-order}`（12 态/8 态状态机词表、开放 API 建单/取消/支付入参）就是词汇表底稿，字段类型按旧表语义对齐后继续用。
2. 路径规范：`/api/{customer|admin|open}/v1/{domain}/{resource}`；webhook `/api/webhook/v1/{provider}`。
3. 统一响应体 `{ code, message, data, traceId }`；分页 `{ page, pageSize, total, list }`。
4. **契约 = 单一事实源**：route 层用 contract zod 做入参校验 + 出参序列化；apps/api 由 zod 生成 OpenAPI 3（后台/开放面）。
5. 认证语义：401 未登录、503 鉴权故障（不 302，防重定向风暴）；CSRF 单一实现。
6. **旧 REST/webhook 语义平移**：`routes/api.php` 67 条（open api、chrome 扩展、webhook）逐条登记到 `contract`，路径与认证语义保持不变（外部调用方零感知）；PHP 侧对应路由下线前保持双活。

## 5. 数据层方案（沿用旧表 + 防腐层）

### 5.1 packages/db 结构调整

```
packages/db/prisma/
├── schema.prisma          ← 活跃：db pull 旧库（174 表）introspect 而来
└── redesign/schema.prisma ← 封存：60 模型新表方案（R2 启用，含 sql/0001~0018 回填脚本）
```

- 生成 client 时只激活 legacy schema；redesign 目录保留演练态，**T0/T1 生产执行全部暂缓**（TODO #3d/#3f 挂起，R2 启动时按 docs/plans/03 既有时序跑，含 precheck 重跑等前置，一行不改）。
- introspect 注意：旧库 utf8mb3、无外键约束、多态列、INT 时间戳——schema 仅提供**形状**，语义靠防腐层补。
- **R2 资产保鲜**：redesign schema 不因封存而腐烂——纳入日常 `pnpm db:generate`（独立输出目录）+ `typecheck`，保证 R2 启动时 schema 与 TS 代码仍对得上；`sql/0001~0018` 随 docs/plans/03 归档不动。

### 5.2 防腐层纪律（repository 是旧表唯一触点）

1. `PrismaClient` 只出现在 domain 的 repository 内；service 层出入参 = contract 类型。
2. **时间戳**：旧表 INT unix 时间戳 → 领域 DateTime 的转换集中在 repository，时区显式 `Asia/Shanghai`（生产 MySQL 会话 `+08:00`，本机 CLI 是 UTC——旧系统实锤过的坑，不许再现）。
3. **collation**：username 等按 `utf8_general_ci` 语义查找（尾空格/大小写折叠），登录行为与旧系统等价；R2 才收紧为 `utf8mb4_general_ci`（届时按 docs/plans/02 的消歧方案走）。
4. **模型硬伤不许洗白**（继承 Java 方案 §4）：`bargainprice` 双语义（Order vs SendOrder）、`goodsprice` vs `goodsprice1`、各域独立 status 状态机——在 repository/contract 里显式命名 + 注释，禁止照搬字段名进领域层；状态机词表用已完成的 12 态/8 态/prostate 9 态。
5. **旧库语义情报直接复用**：docs/plans/00（174 表盘点）、01（v2_ 44 表精读）、finance-schema.md（`dg_record.action` 21 值词表 + 写入点）是防腐层的注释底稿。

### 5.3 金额与密码

- 金额：Prisma `Decimal` 读入 → `utils/money`（Decimal 单入口）计算 → 写回**保持旧精度与旧舍入行为**（复现期不"顺手修正"）；`dg_users.money` 是 decimal(10,2)、实测距上限 65 元——写入口加**溢出守卫 fail-fast**，列不动（R2 改 14,2）。
- 汇率：`dg_huilv.huilv` 是 float——读入即转 Decimal，禁浮点参与计算；充值/折算沿用单据上的旧比率（怪癖登记 R2 清单，新账本必须按当日汇率，见 #11a 第 7 条）。
- 密码：旧库 MD5 无盐——Auth.js credentials 校验 MD5 → **登录成功即透明升级** argon2id；不强制会员重置密码。
- **余额唯一写入口**：即使写的是旧表 `dg_users.money`，也只允许 finance 域一个写方法、守卫下到原子 `UPDATE ... WHERE` + 余额快照校验（复现期纪律，R2/R3 直接继承）。

### 5.4 大表策略（继承 Java 方案 §7.5 + 本仓实测）

| 表 | 现状 | 策略 |
|----|------|------|
| `dg_record`（~800 万） | 仅 `(uid,action,addtime)` 复合索引 | 按 uid+action+时间窗查；单独按 action 全表扫禁用 |
| `dg_order`（14 万+） | `idx_sid` 实测索引失效 | 一律 oid 主键 `IN` 批量路径；禁按 sid 批拉 |
| `admin_operation_log`（亿级） | 旧后台直写 | 新后台操作日志**异步写入 + 分区/归档**，绝不照搬直写 |

### 5.5 写入口切换规则（绞杀核心）

1. **PHP 是唯一写方，直到该域绞杀完成**——该域的客户面 + admin 面 + Job/webhook 全部在 TS 侧上线并通过验收，才整体切写；
2. 切写前在**测试库副本**上跑关键写路径演练（下单扣款、运单五费、充值入账）：同一输入，PHP 与 TS 的副作用逐行 diff；
3. **禁止两系统同写一个域**（含旧 dcat-admin 对该域的编辑入口——切写同时把旧后台对应模块置只读/下线）；
4. MNS 消费权随域移交 worker，移交窗口用消费组 + 幂等键保证不双消费不丢消息（webhook 兜底重试在 worker 侧）。

### 5.6 域绞杀 DoD（每域切写门槛，全项满足才切，缺一即停）

- [ ] 该域**三个入口**（客户面 + admin 面 + Job/webhook）TS 侧全量就绪；
- [ ] 219 PHPUnit 中该域用例 Vitest 等价通过；
- [ ] 测试库副本写路径演练：同输入 PHP vs TS 副作用**逐行 diff = 0**（结果用精确统计核对，禁 `grep -c`，见 MEMORY 血泪坑 2）；
- [ ] §10 安全项复核（后门未复现）；finance 域另加 #11a 逐条对策过审；
- [ ] 灰度方案 + 回退预案就绪（nginx 切流脚本 + 旧路径保活）；
- [ ] 旧后台该域模块置只读/下线，MNS 消费权移交完成；
- [ ] 灰度 ≥2 周业务周期（覆盖月末结算/大促）零告警后才全量。

## 6. 认证设计（三重认证 + 认证中心预留）

- **是什么**：不动数据库，全 TS 把旧系统三个项目（backend/frontend/mzk-frontend）功能 1:1 复现——Next.js 三前台 + Fastify 机器面 API + BullMQ worker，直接读写旧表，按域绞杀 PHP。
