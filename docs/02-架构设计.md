# 02 架构与模块设计

> 状态：设计稿（2026-10-12）
> ⚠ **2026-10-16 修订**：进程拓扑与模块划分以 `docs/04-重写架构方案.md` 为准（新增 apps/api 机器面、域逻辑下沉 packages/domains/*）；本文第五节对账体系后移至 R2/R3 背景。与 04 冲突处以 04 为准。

## 一、为什么是 Monorepo（而非多仓库）

原系统的三个仓库（backend / frontend / mzk-frontend）导致：契约靠口头对齐、类型不共享、前端 9 万+ 文件依赖后端接口却无法在编译期校验。新架构用 **Monorepo 解决三件事**：

1. **契约单点定义**：`packages/contract` 定义一次 API 类型 + zod schema，前后端 + worker 全部引用，编译期保证一致——直接从根上杜绝「改金额参数」这类前后端不一致的漏洞。
2. **数据模型单点定义**：`packages/db` 的 Prisma schema 全仓唯一，所有端共用同一个类型安全的数据库客户端。
3. **AI 会话友好**：AI 在一个仓库内能看到 contract / db / ui 的完整关系，生成的代码跨端一致。

## 二、进程拓扑

```
┌─────────────────────────────────────────────────────────┐
│  apps/web (www)   apps/mzk    apps/admin                │  Next.js SSR
│  前台对日电商      代发端       运营后台                  │
└──────────────┬──────────────────────────────────────────┘
               │  API Routes / Server Actions
               ▼
        packages/contract（契约） + packages/db（Prisma）
               │
       ┌───────┴────────┐
       ▼                ▼
   Redis 队列 ──────► apps/worker（BullMQ 消费者 + 定时）
       │                │
       └───────┬────────┘
               ▼
   MySQL · Redis · 阿里云 OSS / MNS · 钉钉
```

- **三个 Next.js app** 独立部署（不同域名、不同发布节奏），共享 packages。
- **worker 是纯 Node 进程**，不依赖 Next.js，跑队列消费与定时任务（对应旧系统 58 个 Job）。

## 三、packages 职责

| 包 | 职责 | 关键内容 |
|----|------|---------|
| `contract` | API 契约（**核心创新**） | 每个接口的请求/响应 TS 类型 + zod schema；金额用 `branded type` 或精确 `Decimal` 字符串避免浮点误差 |
| `db` | 数据层 | Prisma schema（8 个域的表）、迁移、seed |
| `ui` | 设计系统 | shadcn 组件 + 主题 token，三端共用保证视觉一致 |
| `auth` | 认证 | 会员 JWT、后台 RBAC、代发 dfFlag 分流 |
| `config` | 工程配置 | tsconfig / eslint / tailwind preset |
| `utils` | 通用工具 | 金额计算（**统一入口**）、日期、格式化、幂等 |

## 四、领域模块划分（对应旧系统 8 域）

采用 **模块化单体（modular monolith）**，而非微服务（避免过早拆分）。每个域一个模块，域间通过明确接口交互，禁止跨域直连表。

| 域 | 内容 | 备注 |
|----|------|------|
| `order` | 订单、购物车、砍价、采购 | 核心 |
| `send-order` | 运单、合包、国际发货 | 核心 |
| `finance` | 余额、充值、退款、**对账** | 核心，重点重构（见第五节） |
| `logistics` | 国内物流、日本邮政、物流轨迹 | |
| `member` | 会员、用户、开放 API | 文档最全，**优先试水** |
| `ticket` | 工单、询价 | |
| `cms` | 博客、文章、SEO 页 | 边缘 CRUD，可后置 |
| `wms-gateway` | 库存查询、到货同步（**WMS 的接口面**） | 见第六节 |

> 旧系统里 `Email` 不是业务域，是基础设施，归入 `utils`/`worker` 的邮件通知。

模块内部统一分层：`route`（API 入口）→ `service`（业务逻辑 + 事务）→ `repository`（数据访问）。**事务边界在 service 层，金额计算走 `utils` 单一入口。**

## 五、对账体系设计（针对旧系统「无对账」的补强）

旧系统核心漏洞：`app/` 全目录搜索「对账/reconcile」0 命中，且有 `skip_price_check` 后门 + 后台可手动改价，且改后无账实核对。新系统从根上重做资金完整性：

### 5.1 金额四原则

1. **服务端权威计算**：所有金额由服务端根据「单价 × 数量 + 运费 − 优惠」重算，客户端/第三方回传的金额只作对账参考，**绝不可信**。
2. **Decimal 精确计算**：金额一律用十进制精确类型（Prisma `Decimal` / 字符串），禁止 JS 浮点直接算钱。
3. **金额变更留痕**：任何金额变动写 `ledger`（账本）流水，不可变（append-only）。
4. **改价需强校验**：后台人工改价走独立审批流 + 上下限校验，废除 `skip_price_check` 类后门。

### 5.2 账本模型（ledger）

每笔资金变动记一条流水：`ledger_id | 方向(借/贷) | 金额 | 币种 | 业务单号 | 类型 | 关联单 | 时间 | 操作者`。

资金四流全部落账本：
- **用户侧**：充值（应收/实收）
- **下单侧**：扣款、退款
- **供应侧**：付供应商货款（应付/实付）
- **物流侧**：运费、仓储费
- **汇率侧**：日元↔人民币折算（每笔记录汇率快照）

### 5.3 对账任务（worker 定时）

| 对账 | 比对 | 频率 |
|------|------|------|
| 支付渠道对账 | 平台账本 vs PayPal/Stripe/银行账单 | 每日 |
| 余额对账 | 用户余额变动 vs 订单扣款流水 | 每日 |
| 供应商对账 | 订单应付 vs 1688/淘宝实付回传 | 每单/每日 |
| 物流对账 | 运单费 vs 日本邮政/货代账单 | 每周 |
| 汇率对账 | 折算金额 vs 汇率快照 | 每日 |

**差额处理**：对账不平 → 钉钉告警 → 标记异常 → 冻结相关操作，人工介入。对账结果写 `reconciliation` 表留痕。

## 六、WMS 边界与集成

**WMS 是独立项目（未来 `own/wms`），不并入本 monorepo**。理由：独立业务系统、独立部署、PDA/库内作业形态差异大、稳定性要求高。

主系统只保留 **`wms-gateway` 模块**，负责与 WMS 的接口/事件交互：

```
主系统                        WMS（未来重构，从零写）
┌──────────┐   订单/收货指令   ┌──────────────┐
│ order    │ ──────────────► │ 入库/验货/上架 │
│          │ ◄────────────── │ 库存/到货回传 │
│ logistics │ ◄────────────── │ 出库/合包/发货 │
└──────────┘   事件 + API      └──────────────┘
```

- **主系统 → WMS**：下单后发「待收货」指令；合包/发货指令。
- **WMS → 主系统**：到货、验货、上架、库存变动、出库完成等事件（走 MNS / webhook，**必须幂等**）。
- **契约**：WMS 集成契约也在主系统 `contract` 里定义（共享给未来 WMS 项目），边界清晰。

> 旧系统里内嵌的「轻量 WMS」（`DgArrival`/`DgShelf`/`DgStore`/库存计算）在重写时**不搬进主系统**，其能力归入未来 WMS 项目；主系统只保留 `wms-gateway` 的库存查询/到货同步接口。

## 七、关键 ADR 摘要

| # | 决策 | 理由 |
|---|------|------|
| ADR-1 | Monorepo | 契约/数据/UI 共享 + AI 会话友好 |
| ADR-2 | 模块化单体而非微服务 | 避免过早拆分，域边界用接口而非网络 |
| ADR-3 | WMS 独立项目 | 服务边界而非代码共享 |
| ADR-4 | 金额走 Decimal + ledger | 对账与资金完整性 |
| ADR-5 | contract 单点定义契约 | 编译期杜绝前后端不一致 |
