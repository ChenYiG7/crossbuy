## 四、阶段 1 详细计划（member 垂直切片，试水）

> 选 member 开刀：旧系统文档最全（19 篇）、边界最清、对外接口稳定。目标不是「做出会员」，是**跑通整套新链路**。

**端到端切片 = 一层契约 → 一层数据 → 一层接口 → 一层页面 → 一套测试**

1. **契约先行**（`packages/contract/src/domains/member.ts`）：定义 member 的 Query/Row/Create/Update 类型 + zod（已出样板，按旧接口补全）。
2. **数据层**（`packages/db/prisma/schema.prisma`）：db pull 后按真实表定 Member 模型，`pnpm db:generate`。
3. **接口层**（`apps/web` 的 route）：`route → service → repository`，事务边界在 service，金额走 utils。首个 API 建议是「只读查询」（风险最低）：`GET /api/member/me`。
4. **页面**：web 前台一个会员页（读会员资料）。
5. **测试**：service 单测（Vitest），业务规则走 TDD 红绿循环。
6. **双跑对账**：新接口与旧 GraphQL 接口并行，比对返回一致后切流量。

**阶段 1 出口验收**：member 读接口在新系统端到端跑通，与旧系统双跑，返回一致性通过。

## 五、阶段 2 核心域绞杀顺序（价值 × 知识沉淀）

1. **member**（已试水，推广到全部会员能力）
2. **order + send-order**（核心交易链路，**先补知识再动刀** —— 先完成 #2 知识盘点）
3. **finance（含对账）**（最重，ledger + 四方对账 + 钉钉告警一并落地）
4. **logistics / ticket / cms**（随核心域推进）

每个域：新旧并行 → 数据对账 → 流量切换 → 下掉旧接口。

---

## 六、红线（违反即停工）

- 禁 Big Bang：任何时刻新旧并行，旧系统可回退
- 数据共库：过渡期共用 MySQL，禁双写不同库
- 金额不可信：服务端重算 + Decimal + ledger 留痕
- 幂等：所有 webhook/队列消费幂等
- 旧系统只读：绝不改 `haiou/` 任何文件
