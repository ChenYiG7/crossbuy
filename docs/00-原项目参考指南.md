## 三、读旧系统的优先级（按「重写价值」排序）

1. **`backend/AGENTS.md`** — 领域边界、分层规则、DoD、以及它自曝的领域模型硬伤（见下），读它就能抓住旧系统的设计意图和病灶。
2. **`backend/docs/business/`（实测 67 篇，2026-10-15 核实订正）** — 各业务域的行为规则。**注意分布极不均衡**：member 19 篇（治理最好）、order 4 篇、blog 4 篇。**旧记载「Finance 为 0 篇」不实**：finance 相关实有 4 篇（`finance-orders-bargain-amount-warning.md`、`stripe-recharge-integration.md`、`worldfirst-quota-accumulation.md`、`ecommerce-order-confirm-balance-check.md`，另 `overdue-order-dingtalk-notification.md`）——但都是**单个接入点/单条链路的说明**，没有账本与对账的总纲，域级知识仍需代码逆向（详见 `docs/plans/finance-schema.md` §3.9）。
3. **`backend/database/migrations/`（96 个）** — 数据库表结构与字段语义的权威来源。
4. **`backend/app/Services/` + `app/Models/`** — 业务逻辑与数据模型（`bargainprice`、`goodsprice1` 等歧义字段在这里）。
5. **`haiou/docs/01-系统架构总览.md`** — 系统全景 + 概念对照表。

- ✅ **只读**：旧系统的代码、文档、数据库 schema 一律只读，用于理解业务逻辑。

## 五、从旧系统继承的「必须规避的坑」（速查）

### 领域模型硬伤（`backend/AGENTS.md` 第 9 节自曝）
- `bargainprice` 在 Order 与 SendOrder 中**语义不同**
- `goodsprice` vs `goodsprice1`（原价 / 砍后价），发票优先用 `goodsprice1`
- 各域 `status` 是**独立状态机**，不可跨域假设
- 1688 webhook 可能重复投递，Job 必须幂等

### 对账体系缺失（用户称为「很大的问题」）
- ★ 2026-10-15 逆向精化：旧 `app/` 中**确实没有任何「Σ流水 = 余额」的校验**（`reconcile|checkBalance|对账` 无此类实现），客户余额侧「有流水、无对账」成立——实测账本链断 **7.3%、55% 会员受影响**（`docs/plans/finance-schema.md` §3.6）。但**存在一处真对账实现**：WorldFirst 网关收款 ↔ 待提交付款单的额度匹配（`Services/Finance/MatchWorldFirstCollectionStatementsService.php` + `v2_worldfirst_*` 四表，`docs/business/worldfirst-quota-accumulation.md`），可作新系统匹配算法的范式（该四表在生产 dump 中未见，需核实是否已上线）。
- 后门 `skip_price_check`（跳过单价/数量/砍价三项校验），调用点 `app/Admin/Grids/ExamFailedOrderList.php:140`
- 后台 `BatchUpdateOrder` 可直接改 `bargainprice/sendprice/couponFee`，改后无对账兜底
- → 新系统必须内置：金额服务端重算 + Decimal + ledger 账本 + 四方对账

### 山景私有包无主（比选语言更紧急）
- 6 个 `shanjing/*` 包分发渠道全在山景手里，`vendor/` 未入 git
- `laravel-admin`（2634 文件）= 定制版 dcat-admin = 整个后台骨架
- → 重写前必须 fork 到自有 Git + 自建 composer 私有源

### 禁改清单（旧系统内部）
- `app/Libraries/Malls/VipSdk/`
- `app/Libraries/Taobao/aliyun/AliyunClient.php`
- 前端 `src/main.ts` 的 `__VUE_DEVTOOLS_PLUGINS__` 写入禁用逻辑（不要「修好」）
