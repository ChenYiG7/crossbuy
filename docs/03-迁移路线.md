# 03 迁移路线

> 状态：设计稿（2026-10-12）
> ⚠ **2026-10-16 修订（以 `docs/04-重写架构方案.md` 为准）**：① §1.1「山景包 fork 续命」**作废** → PHP 全面冻结 + vendor 只读冷备（沿 haiou 04 §8 决策）；② 「T0 建新表 → T1 双写」时序整体后移为 R2（数据库重构期）；R1 复现期 = 共用**旧表**、写入口按域切换（PHP 唯一写方直到域绞杀）。客户前台不再「灰度保留旧页」而是重做（URL 1:1 平移保 SEO）。
> 原则：**先续命 → 再接管 → 后按域绞杀**，绝不可 Big Bang 重写。

## 一、迁移前的前置动作（本月，最紧急）

在写任何新代码之前，先保住旧系统的「命」与「知识」：

### 1.1 山景私有依赖续命

旧系统 `backend` 的 6 个 `shanjing/*` composer 包，分发渠道全部在山景手里（私有源 / GitHub / 腾讯云镜像），且 `vendor/` 未入 git。**一旦关停，旧系统连部署都做不到。**

- 6 个包：`laravel-admin`(2634 文件，后台骨架) / `japanpost`(日本邮政) / `dcat-admin-setting` / `laravel-statistics` / `operation-log` / `laravel-filesystem-oss`
- 动作：**fork 全部到公司自有 Git + 自建 composer 私有源**，把 `composer.lock` 的 dist 指向己方。

### 1.2 知识盘点（趁兼职张还在）

旧系统 Finance / Order 域文档为 0（最涉及钱却最没沉淀）。必须趁人还在，产出：

- Finance / Order 域的**业务规则清单**（`bargainprice` 语义、`goodsprice vs goodsprice1`、状态机、砍价/改价逻辑）
- 1688 / 淘宝 / PayPal 等**外部对接的坑**（webhook 幂等、签名、异常状态）
- 对账缺失的**现状盘点**（哪些金额可以被改、哪些环节没核对）

> 这是重写的「原料」，比任何一行新代码都值钱。原料流失 = 重写出来的系统「bug 照旧」。

## 二、分阶段迁移

### 阶段 0：基建搭建（第 1 个月）

- 本 monorepo 的脚手架（Next.js 三 app + worker + packages）
- 数据库：Prisma 连接**现有 MySQL**（只读分析，先不写）
- 契约先行：把旧系统 GraphQL/REST 的**关键接口**在 `contract` 里定义成 TS 类型 + zod（作为新旧对齐的基准）

### 阶段 1：垂直切片试水（第 2-3 个月）

- 从 **member 开放 API 域**开刀（旧系统文档最全、边界最清、对外接口稳定）
- 一个域「前后端 + worker + 契约」端到端跑通，验证整套新链路
- 与旧系统**共用同一 MySQL**，双跑对账

### 阶段 2：核心域绞杀（第 4-12 个月）

按「价值 × 知识沉淀」排序：

| 顺序 | 域 | 说明 |
|------|----|------|
| 1 | member | 已试水，推广到全部会员能力 |
| 2 | order + send-order | 核心交易链路，**先补知识再动刀** |
| 3 | finance（含对账） | 最重，**对账体系一并落地** |
| 4 | logistics / ticket / cms | 随核心域推进 |

- 每个域：新旧并行 → 数据对账 → 流量切换 → 下掉旧接口
- 前台 www **灰度替换**（对日 SEO 收录不能断，新旧前台并行，流量逐步切）

### 阶段 3：前台灰度切换（与阶段 2 并行）

- 新前台与旧前台并行，按 URL / 流量百分比逐步切
- 保留旧系统的 302 规则（`dfFlag` → mzk、`belongCompany=hho` → 1688japan）直到对应端上线

### 阶段 4：旧系统下线（第 12 个月+）

- 全量切换后，旧 `haiou` 仓库进入只读/归档
- 数据迁移收尾：历史订单、财务流水全量迁移 + 核对

## 三、风险与红线

| 红线 | 说明 |
|------|------|
| 禁 Big Bang | 任何时刻新旧必须能并行，旧系统可随时回退 |
| 契约对齐 | 新旧接口契约一致，前端切换时零感知 |
| 数据共库 | 过渡期共用 MySQL，禁止双写不同库 |
| 金额不可信 | 新系统金额一律服务端重算 + ledger 留痕（见架构设计第五节） |
| 幂等 | 所有 webhook / 队列消费必须幂等（1688 会重复投递） |

## 四、里程碑建议

- **M1（第 1 个月末）**：私有包续命完成 + 知识盘点清单产出 + 脚手架跑通
- **M2（第 3 个月末）**：member 开放 API 域在新系统端到端跑通，与旧系统双跑
- **M3（第 6 个月末）**：order/send-order 核心链路切换
- **M4（第 12 个月末）**：finance 对账体系上线 + 旧系统归档
