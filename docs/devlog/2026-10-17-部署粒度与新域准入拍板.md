# 2026-10-17 · 部署粒度与新域准入拍板

> 背景：用户三连问——「全在一个仓库，改后台要整仓重部署？影响客户端？R3 拆多系统影响大？」「接口拆了前后台后端吗？后台发版影响客户后端吗？」「mzk/web 属于 oms 吧？还有 FBA，要不要先建模块？」
> 拍板结论落 `docs/04`（§2 新增关键决策 D3、§3.3 新增新域准入判据）、`docs/06`（M0.8 细化）、TODO #15（FBA 登记）。零代码改动。

- **仓库 ≠ 部署单元**：五 app = 五独立部署单元（各自产物 / 发布节奏 / 进程），无共享后端进程（客户面 API 在 web/mzk 进程内、后台面在 admin 进程内、机器面在 apps/api）；domains/contract 是构建期编译副本、运行时零跨进程 import，运行时唯一共享 = MySQL/Redis。发布影响半径按改动类型分级：app 自身 / packages 只读 / 域写路径（→ 该域写方进程同窗口协同发，非全量重发）；回滚 = nginx upstream 蓝绿秒切。单仓红利 = 所有 app 吃同一份 ui/contract，无多仓版本漂移。
- **端 × 域两轴**：web/mzk/admin/api/worker 是端，oms/财务/CRM 是域分组（R3 按域拆系统、端全部保留为客户端）；「先建模块后填代码」= M0.2 的 11 域骨架已完成，维持现状。
- **新域准入三判据**：独占表族 / R3 独立所有权 / 独立伸缩部署，满足其一才建；**FBA = 业务线非域**（send-order/logistics + platform 的 Amazon 对接 + finance 的编排，挂 mzk 端流程分支），不预建空模块——空域是边界纪律漏洞。M0.8 增「改动类型 → 写方进程集合」的 blast radius 计算。
