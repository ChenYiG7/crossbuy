# 07 开发规范守则

> 状态：2026-10-12 建立（自 system-kit c1~c8 适配到全 TS / Next.js / Prisma 栈）
> 用途：写代码前的检查清单。每条带「代码形态」与「踩坑」，评审时逐条核对。

---

## §1 模块化单体与依赖方向

**规则**
1. 先单体后拆分；拆分预案写死**触发点**（worker 拆进程 / 引入 MQ / 多租户），触发前方案定死。
2. 依赖方向（评审第一检查项）：
   - `apps/*` 之间**禁止互相 import**（三个 Next app + worker 各自独立部署）
   - `apps/*` → `packages/*`（contract/db/utils/auth/ui/config）
   - 业务域之间**禁止横向依赖**，跨域只走 `packages/contract`（实现收口在各自 app 的 service 层）
3. 事务边界在 service 层，金额计算走 `utils/money` 单入口。

**演进触发点写法**（进 docs/06）：
```
> 已识别但现在不做，各自绑定触发点；触发前方案写死。
1. worker 拆分（触发点：拉单量 >N / 平台 API 超时拖垮前台）……
2. 引入 MQ（触发点：多实例部署 / 补偿 Job 出现第 3 个）……
```

**踩坑**：以「将来可能要拆」为由直接上微服务（双倍税）；模块间偷偷 import 对方 service（腐化成泥球）。

## §2 契约层与实现收口

**规则**
1. `packages/contract` **物理隔离**：唯一运行时依赖是 zod，禁 import `@prisma/client` / Next / 框架类型。
2. 契约模型分三类：
   - **只读查询**：`XxxQuery` + `XxxRow`（行视图，敏感字段不出契约）
   - **写侧命令**：`XxxCreate` / `XxxUpdate`（zod schema，`@Builder` 等价物 = zod `.partial()`）
   - **分页**：入参 `pageQuerySchema`（`page`/`pageSize` 自归一并钳制）；出参 `PageResult<T>`（`list` 永不为 null）
3. **权限过滤不信任调用方**：filter 里的数据权限集合（会员/店铺轴）由 service 层强制覆盖装配，调用方自带值忽略。
4. 契约演进：只加字段不改语义；金额用字符串（`Money`），日期用 ISO 字符串。

**踩坑**：契约里出现 entity/ORM 类型 = 没隔离；让调用方传权限集合 = 越权漏洞。

## §3 账本型数据并发正确性（唯一写入口 + 原子 UPDATE 守卫）

> 适用：余额、库存、额度、积分、预付款——任何会被并发加减的列。**这是 finance/ledger 的必修课。**

**规则**
1. **唯一写入口**：金额/数量列只允许一个写方法，类头注释写明红线「禁旁路 update」。
2. **正确性锁落 DB，禁 check-then-act**：一条原子 UPDATE 把算术与守卫全下 SQL，行锁持至提交。
3. **affected=0 必须回查区分两种情况**（禁笼统报错）：
   - 行不存在 → upsert 首建，撞唯一键回退原子 UPDATE 重试一轮；
   - 行存在但守卫不足（余额不够）→ 业务异常，**错误消息带当前值**。
4. **不变量贯穿**：如 `available = onHand - locked`，每条 UPDATE 都过一遍不变量检查。
5. **二级账本同事务**：衍生账（成本/余额快照）只允许被 change() 同事务调用；并发用 `SELECT ... FOR UPDATE` 锁状态行，**锁序单向**防死锁。
6. **账实漂移即拒**：结存为负 = 数据已坏，拒绝动账回滚，禁静默归零。

**Prisma 代码形态**
```ts
// 守卫在 where 的原子 UPDATE
const r = await prisma.account.updateMany({
  where: { id, balance: { gte: delta } },   // 守卫下 SQL：balance - delta >= 0
  data: { balance: { decrement: delta } },
});
if (r.count === 0) {
  const row = await prisma.account.findUnique({ where: { id } });
  if (!row) throw new Error('账户不存在');
  throw new Error(`余额不足：当前 ${row.balance}，需扣 ${delta}`); // 带当前值
}
```

**踩坑**：先 SELECT 判余额再 UPDATE（超卖）；`count=0` 统一报「余额不足」（行不存在与守卫不足混报）；旁路 updateById 改数量列（野生）。

## §4 状态机与条件更新守卫（cas）

> 适用：订单、运单、工单、审批单等有状态单据。旧系统「各域 status 独立状态机」的坑，本条给正解。

**规则**
1. **条件更新即守卫**：`UPDATE ... SET status=to WHERE id=? AND status=from`，`count>0` 即推进成功。
2. **一台单据多台状态机 = 多列各自 cas**：业务状态 `orderStatus` 与审核状态 `reviewStatus` 是两台机器，守卫各自独立，**不合并**。
3. **人工结论不被同步覆盖**：平台同步/upsert 更新清单**显式排除人工列**（审核人/审核备注/人工状态）。
4. 状态列注释即拍板表：枚举含义写进 schema 注释与 contract 常量，三方对齐。

**Prisma 代码形态**
```ts
const r = await prisma.order.updateMany({
  where: { id, orderStatus: 'WAIT_PAY' },   // cas 守卫
  data: { orderStatus: 'PAID' },
});
if (r.count === 0) throw new Error('状态已变更，请刷新重试');
```

**踩坑**：状态推进用「先查后改」（并发下别人已通过）；多状态机塞一列（`status>2` 表已审核）；upsert 忘排除人工结论列（平台重拉冲掉人工审核）。

## §5 第三方对接防腐层（SPI + 统一模型 + 网关横切）

> 适用：1688 / 淘宝 / Shopify / Rakuten / TheBase / PayPal / 日本邮政 / MNS。两个以上对接方时，本条从「建议」升级为「必做」。

**规则**
1. **包结构即纪律**：对接代码收口在一个模块，`adapter/<vendor>/` 内「Client 门面 + Translator 翻译 + Token/Signer」。
2. **Translator 只翻译**，出现 `if (业务)` 即防腐失败（平台差异只许存在于 Translator）；统一中间模型 `Unified*` 落库方只依赖 unified 模型。
3. **raw_json 必存原始报文**（翻译错可回溯重翻）；核心字段成列；禁为外部对象建全套镜像表。
4. **新增第三方 = 新增一个实现类**，主系统零改动；门面默认关（`enabled=false`），凭证到位才开。
5. **凭证安全**：token/secret 只走统一凭证入口（AES-GCM 加密，唯一写入出口）；日志/异常不含凭证。
6. **拉单三板斧**：按**对方侧「更新时间」**窗口拉；游标 = 拉取日志最近成功 `window_end` 左叠 5 分钟；幂等靠业务唯一键 upsert，禁先查后插。
7. **AFTER_COMMIT 外呼**：本地事务内只发事件，事务提交后才调外部 API；失败只记日志表可补，不回滚本地。
8. **限流横切**：维度 =（第三方，接入主体，桶类型）；令牌桶状态落 Redis；fail-open（保护性横切，基础设施故障不绑架业务）与 fail-closed（真超限 429）分层。

**踩坑**：在业务 service 里直接调外部 SDK（字段散落全仓）；Translator 里写业务分支；事务内调 HTTP（拖死本地事务）；凭证进日志。

## §6 schema 正本与迁移纪律

**规则**
1. **单一正本** = `packages/db/prisma/schema.prisma`；所有表/列/索引只改这里，改完 `pnpm db:generate`。
2. **建表规约**：每表带 `id / created_at / updated_at`；逻辑删除 `deleted_at DATETIME NULL`（NULL = 未删；全仓 60 模型一致，**不用** `deleted BOOLEAN`）、**金额 `Decimal(14,2)`**（2026-10-15 Q8 定版：原写 12,4，实测旧库最大余额 99,999,350.04 距 `decimal(10,2)` 上限仅 64.95 元，扩整数位防溢出；客户面金额本就 2 位小数，分摊尾差是「分」级，无 4 位需求）、汇率 `Decimal(12,8)`、**币种列必带且禁跨币种加减**、状态列注释写明枚举；**禁外键与级联**；业务唯一键必须建（幂等的根本）。**append-only 表（`ledger_entries` + `order_status_histories` / `send_order_status_histories`）是本规约的例外**：不给 `updated_at`/`deleted_at`，更正靠加反向分录。
3. **三方防漂移**：schema ↔ 设计文档（docs/03）↔ contract 常量，改一处同步其余。
4. **自定义 SQL 真库验证**：Prisma `$queryRaw` / raw 语句必须在开发库真跑一遍，mock 测不出方言错误。
5. **迁移工具**：过渡期「正本 + db pull 对齐」；多环境/多人后升级为版本化迁移（拍板项）。

**踩坑**：schema 与文档各改各的；手工 ALTER 无台账；金额用 float/double（精度事故）。

## §7 依赖钉版本与坑位注释

**规则**
1. 共享依赖版本收敛到 `pnpm-workspace.yaml` 的 `catalog:`，子包引用 `catalog:` 不写具体版本。
2. 非显然的版本钉必须带**坑位注释四要素：编号/日期/原因/解除条件**（尤其是传递依赖被拉低的隐性炸弹）。
3. 升级只动 catalog 一处；引入新依赖后核对关键件版本。

**踩坑**：只钉版本不写原因（半年后不知道能不能升）；子包写死版本号（升级漏改，运行期两个版本共存）。
