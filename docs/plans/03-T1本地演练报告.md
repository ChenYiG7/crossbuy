## 四、演练暴露的 4 个真实问题（都已修）

1. **`ALTER TABLE ... AUTO_INCREMENT = (子查询)` MySQL 不允许** → 改为 `PREPARE`/`EXECUTE` 预处理语句。
2. **Coding 笔误 `UNIONS`**（校验 SQL）→ 修。
3. **字符集/排序规则必须显式转换**：`LOWER(TRIM(uname))` 是 utf8mb3，套 `utf8mb4_*` 排序规则会报 1253 → 必须 `CONVERT(... USING utf8mb4)` 后再 `COLLATE`。
4. **本机 MySQL 9.7.2 无 `MD5()` 函数**（`FUNCTION xxx.MD5 does not exist`）→ 校验改用直接字段比对；**迁移 SQL 一律不用 DB 端 MD5**。

## 五、★ 重大发现：collation 决定重名口径（8 vs 24）

在 **22,612 个真实用户名**上实测四种排序规则的重名组数：

| 排序规则 | 重名组数 | 说明 |
|---|---|---|
| `utf8mb4_general_ci`（≈ 旧库 `utf8_general_ci`） | **8** | 与已完成分析的消歧方案一致 |
| `utf8mb4_unicode_ci`（T0 生成 DDL 的表级默认） | **24** | 额外 16 组 |
| `utf8mb4_0900_ai_ci`（MySQL 8 默认） | 23 | 同上 |
| `utf8mb4_bin` | 8 | 但破坏 ci 登录语义，不可用 |

**多出的 16 组 = 同一人在「全角/半角」「片假名/平假名」「全角空格 U+3000」下的两次注册**，例如 `LAKI`/`ＬＡＫＩ`、`かず`/`カズ`、`Keep trying`/`Keep　trying`。

**但其中有多对是「不同人」**：

| 组 | 账号 A | 账号 B | 判断 |
|---|---|---|---|
| RYUJI | uid 1801 `ＲＹＵＪＩ` 渡辺様（815 单 / ¥1489.01） | uid 7874 `Ryuji` 深澤竜二（2 单） | **不同人** |
| まつ | uid 1996 `マツ` 松園様（100 单） | uid 21691 `まつ` 松岡司様（384 单） | **不同人** |

→ 若用 `unicode_ci`，会**强制把不同人的账号折并/改名**，属真实用户误伤。

**决定：`member.username` 显式定为 `utf8mb4_general_ci`**（`packages/db/sql/0001a-member-username-collation.sql`）——
① 与旧库逐字一致，**零行为变更**；② 维持已确认的 8 组消歧；③ 不误伤 16 组里那些"不同人"。

**本地语义验证（应用 0001a 后）**：

| 测试 | 期望 | 实测 |
|---|---|---|
| `かず` 与 `カズ` 能否共存（假名不折并） | 能 | ✅ 2 行并存 |
| 插 `a1a1`（`A1a1` 已存在）| 应报 Duplicate | ✅ `Duplicate entry 'a1a1'` |
| 插 `Ａ１Ａ１`（全角，`A1a1` 已存在）| 应允许（不折并） | ✅ 允许 |

**约束（已写进 0001a 注释）**：`username` 与其他 `utf8mb4_unicode_ci` 列混用会报 `Illegal mix of collations` → **禁止把 username 与其他字符串列 JOIN/UNION**；只与字面量/参数比较。

### 9.2 ★★ 缺陷：`INSERT..ON DUPLICATE KEY UPDATE` 会吞账号并篡改余额（已修）

`member.username` 是 UNIQUE。未进 `_fix` 的重名对，第二行撞车后**不报错、也不新插一行**，而是走 ODKU 把**前一个账号那一行整行覆盖**——`balance = u.money` 取的是**后一个账号**的钱。

- 本地实测后果：**5 个账号消失**（member 5,016 vs 源 5,021）+ **2 个余额被清零**（uid 6932 的 `100.18 → 0.00`、uid 18213 的 `19.96 → 0.00`），**全程零报错**。
- 本质：username 撞车恰恰意味着「**这是两个不同实体**」，而 ODKU 的语义假设是「同一实体的重复投递」。这是 AGENTS 铁律 3 的**反面变体**——唯一键 upsert 用错了实体边界。
- 修法：`0002` §2 之前加 fail-fast 守卫（存储过程 `_guard_username_disambiguated`，发现残留撞车即 `SIGNAL SQLSTATE '45000'` 中止）。本地实测：生产版脚本 **rc=1 中止并精确报出 5 组**；补齐映射后全链跑通、余额与源分毫不差。

### 9.3 守卫必须按**目标列 collation**判碰撞（新坑）

源 `dg_users.uname` 是 `utf8mb3_general_ci`，目标 `member.username` 是 `utf8mb4_general_ci`——**同名不同族**：实测 `'なおたろう' = 'ナオタロウ'` 在 `utf8mb3_general_ci` / `utf8mb4_unicode_ci` 下为 **1（相等）**，在 `utf8mb4_general_ci` 下为 **0（不等）**。按源 collation 判会**误中止** 2 组假名/片假名账号（它们在目标索引下其实可以共存）。⇒ 唯一性断言一律按 `CAST(... AS CHAR CHARACTER SET utf8mb4) COLLATE utf8mb4_general_ci` 分组。

### 9.4 遗留 4 项 FAIL 的定性：期望值写死了生产快照

`A1 8→7`、`A3 残留 5`、`B6 改名 8→7`、`B7 合并 1→0` 都**不是回填错**：本地 `taotaro` 副本与 Q4 扫描（2026-10-13）时的生产快照不是同一份（本副本没有 Haru0128/15274 等账号，重名组 7 个而非 8 个）。⇒ 待办：verify 的期望值改为**按当前源实时计算**，否则演练永远与快照打架（登记 TODO **#3g**）。

### 9.5 `member_address` 回填缺 JOIN 过滤（B12 WARN 定性）

本地 B12 悬空 2 行（`member_id` 1001/1002），查源：这两个 uid **在 `dg_users` 里根本不存在**——是当年手工 mock 的残留。但脚本本身**没有 JOIN member 过滤**，所以生产上只要存在孤儿地址就会同样落悬空行，使 Prisma `include` 报错（违反回填铁律①）。⇒ 一并登记 #3g。

### 9.6 对 #3d（交 DBA 落库）的硬约束

**T1 执行前必须重跑 `precheck-username-duplicate.sql`**（Q4 是 2026-10-13 的快照，之后每天仍可能有新重名注册），把新出现的重名组补进 `_fix`。没补的话现在会**被守卫直接拦停**，而不是像之前那样「静默成功后丢账号改余额」——这正是这次复跑最大的收获。
