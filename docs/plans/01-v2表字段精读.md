## 〇、全局结论（先看这段）

### 0.1 三个「名不副实」的表（最容易踩）

| 表名                      | 直觉理解     | **实际是**                                                       | 处置                               |
| ------------------------- | ------------ | ---------------------------------------------------------------- | ---------------------------------- |
| `v2_address`              | 会员收货地址 | **行政区划字典**（level 1国家~5街道），与 `v2_area` 结构完全相同 | ❌ 不是 member 域；是共享 geo 字典 |
| `v2_area`                 | 地区         | 同上，`v2_area` 是 `v2_address` 的新代重写（PK 由复合改单列）    | 二选一，保留 `v2_area` 语义        |
| `finance_order_cash_flow` | 订单流水     | 会员**现金流水**（uid+utype+change_type），不是订单行            | ✅ 是 finance 域的对账原料         |

**真正的会员收货地址在 `dg_address`（老代表）；真正的会员主表在 `dg_users`（老代表）。** v2_ 里根本没有会员主表——这解释了为什么 member 域「开放 API 文档最全」却「表最少」。

### 0.2 五类跨域硬伤（重写必须避）

1. **金额列精度不统一**：`DECIMAL(10,2)`（dg_users.money / v2_ecommerce_product_sku.price）、`DECIMAL(12,2)`（v2_member_webhook.balance_low_threshold / v2_platform_order_amount.*）、`float(10,2)`（v2_order_detail.coupon_fee、dg_favorite.goodsprice）、`varchar(50)` 存「价格+币种」（v2_ecommerce_order.price）。
2. **时间戳双制式**：老代表（dg__）用 `INT` unix 秒（regtime/logintime/stoptime/validity）；新代表（v2__）用 `DATETIME`/`TIMESTAMP`。混用是必然，重写一律 `DateTime`。
3. **软删除三套并存**：`deleted_at`（v2_ecommerce__/v2_oauth__）、`deleted_at`+`restored_at`（v2_ecommerce_shop 可恢复）、无软删（v2_favorite）。
4. **多态外键（Laravel morph）**：`v2_favorite.favoriteable_type/id`、`v2_ticket.ticketable_type/id`、`v2_personal_access_tokens.tokenable_type/id`。跨域引用，重写要么收口成显式列，要么保留但契约层禁暴露。
5. **`status` 各域独立状态机**：`v2_ecommerce_shop.status`(0待审核/1激活/2暂停/3已删除) ≠ `v2_ecommerce_order.order_status`(-1/1/2) ≠ `v2_ticket.status`(1~4) ≠ `v2_logistic_domestic.state`(0/1/2)。**不可跨域假设**。

### 1.0 根表 `dg_users`（会员主表，uid 主键）★

老代表，`AUTO_INCREMENT=25289`。字段极多，按用途分组：

**身份/登录**

- `uid` INT PK AUTO_INCREMENT — 会员主键
- `uname` VARCHAR(50) NOT NULL — 登录名。**只有普通 KEY 无 UNIQUE（坑 1）**

- `apitoken` VARCHAR(50) + `tokenexpiretime` BIGINT — **老 API token（与 v2_personal_access_tokens 并存两代）**

- `state` SMALLINT DEFAULT 1 — 状态
- `validity` INT NOT NULL — 有效期

**资金（★ 红线区）**

- `scores` INT DEFAULT 0 — 积分
- `floatrate` DECIMAL(10,2) DEFAULT 0.05 — **对客浮动汇率（在基准汇率上加该值）**
- `orderenable` TINYINT DEFAULT 1 — 0 不可交易 / 1 可交易
- `stoptime` INT — 终止时间

**代发属性（dfflag 家族）**

- `dfsendaddress` / `dfsendtel` / `dfsendname` — 代发发件人
- `csvupflag` TINYINT — CSV 上传开关

**业务身份**

**联系方式/资料**

- `tname` / `enname` / `face`(头像) / `sex` / `tel` / `zip` / `card` / `address` / `qq` / `msn` / `country` / `city` / `line` / `wechat`

- `reg_extra` VARCHAR(1024) — 注册附加信息

**邮件/通知**

- `mail_frequency` TINYINT DEFAULT 4 — 到着邮件 1实时/2每小时/3每6小时/4每天
- `email_subscribe_status` INT — **二进制位运算控制订阅（坑 4：位标记语义不在 dump 里）**
- `cc_emails` JSON — 抄送邮箱

**仓储/其他**

### 1.2 `v2_member_webhook`（会员 webhook 配置）

`AUTO_INCREMENT=2`（新功能，用量少）。

### 1.3 `v2_member_webhook_delivery`（webhook 投递队列）★

**出站 webhook 的幂等队列**，是 worker 的核心作业表。

- `id` BIGINT UNSIGNED PK；`uid`；`event` VARCHAR(64)（事件名）
- `event_key` VARCHAR(191) **UNIQUE** — 去重键：「同一事件只发一次」

- `next_attempt_at` TIMESTAMP — 下次发送时间；`delivered_at` TIMESTAMP

### 1.4 `v2_personal_access_tokens`（Laravel Sanctum PAT）

- `id` BIGINT UNSIGNED PK；`tokenable_type`/`tokenable_id`（**多态**，指向 Member）

- `abilities` TEXT；`last_used_at`/`expires_at`/`created_at`/`updated_at`
- INDEX `(tokenable_type, tokenable_id)`
- ⚠️ 与 `dg_users.apitoken` 是**两代令牌机制**，重写需二选一（建议统一为新 PAT + 哈希存储）

### 1.5 `v2_open_api_idempotency`（开放 API 幂等）★

- `id` BIGINT UNSIGNED PK；`uid`；
- `scope` VARCHAR(32) — **`orders` 下单 / `send_orders` 配送委托**
- `client_key` VARCHAR(64) — 客户防重键（client_order_id / Idempotency-Key）

- `status` TINYINT DEFAULT 0 — 0 处理中 / 1 完成
- `response` JSON — 首次结果（第二次起**原样返回**）
- **UNIQUE `(uid, scope, client_key)`**
- ➡️ 重写直接照搬：这就是「幂等消费」的标准实现（也适用于 webhook/队列）。

## 九、`finance_order_cash_flow`（财务现金流水）★★

- `id` BIGINT UNSIGNED PK；`uid` INT（用户 id）；`utype` TINYINT（用户类型）
- `change_type` TINYINT — **操作类型（枚举值不在 dump 里，需从代码反查）**
- `price` DECIMAL(10,2) — **用户付款**；`send_price` DECIMAL(10,2) — **运费**；`paid_money` DECIMAL(10,2) — **财务付款金额**；`bargain_price` DECIMAL(10,2) — **砍价金额**
- `operator` INT（操作人）；`created_at`/`updated_at`
- INDEX `operator`、`uid`、`change_type`
- `AUTO_INCREMENT=1020212`（百万级）

**关联**：`relation_order_and_finance_order_cash_flow`（`cash_flow_id` ↔ `oid`）多对多，`AUTO_INCREMENT=2612089`。

**诊断**（对应旧系统「有流水无对账」）：

1. **一笔流水承载 4 个金额语义**（付款/运费/财务付款/砍价）——无借贷方向、无余额、无币种列。
2. **无对账锚点**：无「对账批次」「差异」「冻结」字段，也无独立 `reconcile` 表。
3. **`change_type` 语义是外挂的**（依赖代码常量），schema 无枚举约束。
4. ➡️ 重写处置：**不照搬此表**，用 `ledger_entries`（账户+方向+带符号金额+余额快照）+ 对账批次表替代；此表仅作**历史数据回灌 + 对账差异核验**的原料。
