# 09 — 交易链路状态机（M2 前置知识盘点）

> 2026-10-17 由旧代码全量扫描提取（`app/` 下 85 处 `'state' =>` 写点逐一甄别，排除 tests）。
> 配套：金额语义见 `03-order-schema.md` §3.5（bargainprice 双语义/砍价联动）；表属主见 `07`。
> 用途：M2 交易链路动刀的**行为正本**——R1 复现以本文为对照，禁止凭感觉发明状态规则。

## 〇、三个域，三台独立状态机

| 域     | 表.字段                                                  | 取值                             | 驱动来源                                                               |
| ------ | -------------------------------------------------------- | -------------------------------- | ---------------------------------------------------------------------- |
| 订单   | `dg_order.state`                                         | 1~12                             | 入站 webhook（1688/淘宝全球购/Chrome 插件）+ 用户面 GraphQL + admin 面 |
| 运单   | `dg_sendorder.state`                                     | 1~8（+ 伴随字段 `bargainstate`） | 用户面（付运费/确认收货/取消）+ admin 面（发票/邮寄/批量）             |
| 导入单 | `dg_imporder.state`（+ 明细 `dg_imporder_detail.state`） | 0~3 / 0~5                        | 用户提交导入 + admin 确认下单                                          |

**MNS 不驱动任何内部状态流转**——`MnsMessageService` 只承载 3 个**出站**事件：`order.created`（下单成功）、`send_order.created`（运单生成）、`send_order.paid`（付运费后）。内部流转全部由**入站 webhook + 用户/管理员动作**驱动。这直接决定 M3 的 worker 接管范围：MNS 是通知面不是控制面。

### 1.2 关键语义裁定

- **6 与 10/11 的分工**：6 = 「admin 拉无效后的待处理池」；6→10 只能**用户本人**取消（返金），6→11 只能 admin 废弃（不返金）。二者由**操作主体 + 是否返金**区分。admin 没有任何入口直写 10。
- **9 与 12**：12 = 检品发现问题待确认（custowaittime），9 = 确认后不良对应中（custotime）。12→9 有三个入口；**9→12 唯一路径**是 `BatchSetAfterSales` 把有检品记录的售后单打回。
- **5 的回退**：只有「取消运单」一条路（5→4），且依赖运单还在 WAITING。admin 批量编辑不允许 5→4/3；`BatchUpdateOrderState` 只开放 →1/→2 两个方向。
- **状态 8 是死状态**：全 `app/` **无任何写点**，只有读取（报表、无效单列表、webhook 扫描器按 `state=8 AND uptime>=since` 推事件）。admin 拉禁运实际走 **state=6 + item_location 禁运原因**。→ 已登记怪癖（08 §一 S17）。
- **purchase_type（0 一键/1 手动/2 自动）不是状态机**：AUTO=2 **全库无写点**（死常量）；MANUAL=1 唯一写点是采购员手动补 tid 时（`BatchUpdateOrder:317-326`）。所谓「一键→自动下单」其实是 1688 入站 webhook 推着 order.state 1→2→3 走。→ S18。
- **采购失败/缺货无自动流转**：只发通知（`NotifySupplierProductStockOutJob`），订单停在 1，需人工拉无效 → 用户取消返金。

### 2.2 bargainstate 不是状态机，是「action=11 流水存在性」的伴随标志

- 定义 `SendOrder.php:164-170`：0=未返砍金、1=已返。
- 置 1 的两个写点：**发送发票时**（`EditFapiao*:1218-1245`）与 **DF 批量邮寄时**（`BatchUpdateDFSendorder:312-335`）。
- 判重依据是 `dg_record.action=11 AND remark like '%送り状 {sid} 商品%'` 的流水存在性（`hasBargainRefundRecord`/`ensureBargainStateConsistency`，发送发票前兜底纠正）——**幂等靠流水反查，不靠唯一键**。
- 与 08 §一已登记的 S14（先查后插判重）同族：**R1 照抄、R2 给 (sid, action) 流水唯一键**。

## 四、⚠ 竞态风险点清单（先查后改 TOCTOU）——R1 复现时逐点标注

旧系统的状态守卫绝大多数是「读集合到内存 → PHP 校验 → 批量 UPDATE」，**UPDATE 语句不带 from-state 条件**：

| 写点                                                                                                                                           | 风险                                                                       | R1 处置                                                             |
| ---------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| webhook/插件发货同步 `Api/OrderController:481,711,2311,2380,2471`                                                                              | 查 `state=2` 拿 oid 后 UPDATE 不带 state 条件 → admin 同时改单会被强写为 3 | **1:1 复现**（webhook 行为分叉会破坏对账）；标注 + 运行时对账盯差异 |
| admin 批量表单（BatchUpdateOrder/ForCheck/State/BatchSetAfterSales）                                                                           | 无锁、UPDATE 无 state 守卫；`updateOrder` 内部 :927 重读也未加锁           | 同上；admin 面并发概率低，灰度期盯                                  |
| `ConfirmAfterSalesForm:44-54`                                                                                                                  | 读=12 后无条件 update，与 BatchSetAfterSales 并发可重复迁移                | 1:1                                                                 |
| `SendOrderCancelService:29-40`                                                                                                                 | 运单锁缺失，与提交配送并发可能互踩                                         | 1:1（用户面低频）                                                   |
| `BindOrder:47-84`                                                                                                                              | Cache::add 锁挡不住其他入口穿插                                            | 1:1                                                                 |
| `BatchUpdateOrderForCheck:226-229`                                                                                                             | **只校验第一单** state=3，批量其余不校验                                   | 1:1（弱守卫，登记）                                                 |
| **范本（对照）**：`update1688PaidOrders:821-830`（条件 UPDATE）、`OrderCancelService`（行锁+终验）、`CreateMemberSendOrderService`（订单行锁） | ——                                                                         | 新代码模式来源                                                      |

**原则**：R1 状态写点一律 1:1（守卫强弱差异本身是行为）；R2 收敛 = 全部改「条件 UPDATE + 行级锁」，收敛清单以本表为准。逐条登记见 08 §一 S19（TOCTOU 族）。

## 五、对 M2/M3 的影响清单

1. **契约**：`contract/domains/order.ts` 的状态词表必须 1:1 对齐 §1.1（含 8/12 这类「读得到写不进」的值）；send-order 词表含 bargainstate。
2. **守卫正本**：本文件 §1.1/§2.1 的「守卫要点」列 = TS service 层迁移校验的逐条验收标准。
3. **M3 worker**：MNS 只有 3 个出站事件（`MnsMessageService:24-28`）；webhook 入站 5 个族（1688 支付/发货、淘宝全球购 DG/DF/ZY、国际物流建档、LogisticWebhook 只改 dg_arrival）。worker 接管范围据此定界。
4. **对账**：资金动作写点共 4 处（下单扣款 ACTION_1、取消返金 ACTION_4、付/扣运费 ACTION_3、砍价返金 ACTION_11）——运行时对账断言只挂这 4 个动作 + bargainstate 一致性兜底。
