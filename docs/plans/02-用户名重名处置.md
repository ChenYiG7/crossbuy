## 二、为什么是 8 组（排序规则是关键）

旧库 `dg_users.uname` 的排序规则是 **`utf8_general_ci`** —— **大小写不敏感 + 尾部空格不敏感**。所以：

- `PEYANG `（尾空格）与 `peyang` 会被视为**同名**；` shkomatsuzaki`（前导空格）与 `shkomatsuzaki` 则**不算**同名（前导空格在 ci 下有效）。
- 我们的新表 `member` 用 **`utf8mb4_unicode_ci`**（同为 ci），UNIQUE 判定口径一致 → 必须按 `LOWER(TRIM(uname))` 归并来消歧。

按 `LOWER(TRIM(uname))` 归并后，撞车正好 **8 组**（= 重名明细 7 组 + 前导空格 1 组），与旧库 ci 语义完全吻合。

> ⚠️ **踩坑**：判断「尾部空格」不能用 `uname = TRIM(uname)` —— ci 排序下 `'a ' = 'a'` 为**真**，会漏判。必须用 `CHAR_LENGTH(uname) = CHAR_LENGTH(TRIM(uname))`。此坑已写入消歧 SQL 注释。

## 四、消歧规则（确定性，无需人工也能跑）

1. 归并键 = `LOWER(TRIM(uname))`（ci + 去首尾空格）。
2. 每组**保留者**按优先序：`有余额` > `有订单` > `原值本就无首尾空格` > `注册更早` > `uid 更小`。
3. 保留者用户名 = `TRIM(原值)`（保留原大小写，仅去空格）。
4. 其余账号：`TRIM(原值) || '_' || uid`。
5. 改名只发生在 **T1 回填写入新表 `member`** 时，**绝不 UPDATE 旧库 `dg_users.uname`**。

> 为什么用 `_<uid>` 后缀：与旧名可读关联、几乎不可能撞车；T1 回填时仍会做一次唯一性兜底校验。

## 六、对设计的影响（3 条要落到 schema / 迁移）

1. **`member.username` 的排序规则要显式定**：建议跟随旧语义用 **ci**（`utf8mb4_unicode_ci`，与新表默认一致）。
   - ⚠️ Prisma schema **不原生支持列级 collation**，需在迁移 SQL 里用 `ALTER TABLE member MODIFY username VARCHAR(50) CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci NOT NULL`（或在建表后 raw SQL 补）。
   - 若改用 `utf8mb4_bin`（区分大小写），撞车组会从 8 降到 5，但会**改变登录行为**（旧系统是 ci）→ 不推荐。
2. **`member` 建议补两列**（additive）：
   - `username_original`（VARCHAR，可空）：记录改名前的原名，便于客服/审计；
   - `username_auto_renamed`（TINYINT 默认 0）：标记因重名被自动改名者，登录时提示。
3. **email 不给唯一约束**：`123456@qq.com` 出现 **31 次**（uid 19544–19574，疑似测试号）、另有大量 2 次重复 → email 只能普通索引；登录建议支持「用户名 **或** email」。
